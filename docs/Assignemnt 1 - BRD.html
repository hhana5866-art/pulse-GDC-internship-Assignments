User Registration with Email OTP

A user signs up with an email and a password, receives a six-digit code by email, and only becomes a real account once that code checks out.

01What you're building

Anyone can type any email address into a signup form. Without a verification step your user table fills up with typos that never reach a human and addresses belonging to other people. So a registration only becomes an account once the person proves they can read mail sent to that address. Until then it is a temporary, expiring intention to register — not a user.

In scope

  • Starting a registration with an email and password
  • Generating, sending, expiring and verifying the code
  • Resending a code, with limits
  • Creating the account once the code is verified
  • A consistent response shape everywhere, and a schema managed as versioned migrations

Not in scope — don't build these

  • Login, sessions or JWTs
  • Password reset
  • Any frontend — this is an API only
  • Social login, roles, permissions, deployment
Every year someone spends two days on a login endpoint nobody asked for, then runs out of time for the things that were written down. Read that second list twice.

02How it must behave

FR-1Starting a registration takes an email and a password, and returns an id used by the calls that follow.
FR-2The code is six digits and expires on its own — with no cleanup code written by you.
FR-3The password is hashed before it is stored anywhere, including while the registration is still pending. Plaintext never reaches the database, Redis, a log line or an error message.
FR-4The code is delivered by real email. Printing it to the console or returning it in the response is not delivery.
FR-5An account is created only when a correct, unexpired, unused code is submitted.
FR-6One usable code at a time. Issuing a new one kills the previous one immediately.
FR-7Wrong attempts are counted. At the limit the code is dead — even if the correct value arrives afterwards.
FR-8Resending is limited by a cooldown and a daily cap per address.
FR-9A pending registration never sits in the users table, and an abandoned one never blocks the real owner of that address from registering later.
FR-10Starting a registration responds identically whether or not the address already has an account.If it does exist, send that person a "someone tried to sign up with your address" email instead of a code.
FR-11Verification and account creation succeed or fail together. If creation fails, the code is not consumed and the user can retry.
FR-12Emails are stored and compared trimmed and lowercased, so Ali@X.com and ali@x.com are the same person.

A pending registration outlives a single code on purpose — it has to survive a resend.

04Response envelope

Every response — success or failure — comes back in the same envelope, with exactly one of the two fields filled in.

{
  "result": { ... }  or null,
  "error":  { ... }  or null
}

Success fills result and leaves error null. Failure fills error and leaves result null. Both filled is a bug. Both null is a bug.

200/201/202                          any failure
{                                    {
  "result": { ... },                   "result": null,
  "error": null                        "error": {
}                                        "code": 3001,
                                         "message": "The code is not correct."
                                       }
                                     }
E-1Every response uses it — including 500s, and including errors Spring produces before your code runs: unknown routes, wrong method, malformed JSON.That last group is the interesting part. Those don't go through your exception handler — find out where they do go.
E-2Exactly one of result and error is non-null. Never both, never neither.
E-3error.code is a number from the catalogue below, serialised as a number and not a string.
E-4error.message is safe to show a user. No stack traces, class names or SQL — in any profile.
E-5Built in one place, not assembled inside controllers. HTTP status codes still mean what they should — never 200 OK with an error inside.
E-6When several fields are invalid, the message names all of them, not just the first.

Never return the code. Not in a response, not in a header, not in a log line, not "just while testing". A code visible anywhere but the recipient's inbox defeats the whole feature.

06Rules to work within

These push you toward tools you haven't used yet. None of them names the library that solves it — finding that is part of the work.

C-1Starting the app against an empty database must build the whole schema. ddl-auto must be validate or none, and running SQL by hand doesn't count.Your reviewer will drop the database, start your app, and expect the schema back.
C-2No hand-written SQL for ordinary lookups and saves. Your data access layer should be interfaces, not classes you wrote.
C-3Codes and pending registrations must expire by themselves. No scheduled task, no background sweeper, no "delete where expired".This rules out PostgreSQL for them. Something else in your compose file does exactly this.
C-4Real SMTP. The compose file runs a mail server with an inbox at localhost:8025 — your codes must land there as actual messages. Pointing at a real provider instead must be configuration, not a code change.
C-5Nothing secret in the repository. Configuration comes from environment variables, with a committed example file listing the names.
C-6A clean clone runs with the commands in your README, on a machine that has never seen your project.
C-7Input is validated declaratively at the edge, before any business logic or database call runs.

07When it's done

Priorities, not grades. Level 1 is the foundation. Level 2 is where most of the learning is. Level 3 is there if you finish early.

Level 1Build this firstEverything depends on it
  1. Empty database plus your README steps → the app starts and the schema is created automatically.
  2. A valid signup returns 202 with a registrationId, and a real email with a six-digit code arrives.
  3. The correct code in time returns 201, and a user row exists holding a BCrypt hash.
  4. A wrong code returns 400 with code 3001, and no user is created.
  5. Someone abandons a registration for an address; the real owner can still register it later.
  6. Drop the database, restart the app, and the schema comes back with no manual steps.
  7. The plaintext password appears nowhere — not in the database, not in the logs.
Level 2Where the learning isAim to reach all of these
  1. A code older than five minutes returns 410 / 3002, and it has left storage without any cleanup code of yours.
  2. A sixth wrong attempt returns 429 / 3003 — and the correct code no longer works either.
  3. Resending inside the cooldown returns 429 / 4001.
  4. After the cooldown the new code works and the old one doesn't.
  5. A bad email and a short password in one request return 400 / 1001 naming both problems.
  6. Every response is the envelope — including a mistyped URL and a malformed JSON body.
  7. Sending the email doesn't hold up the response — a slow mail server doesn't make the API slow.
  8. With the mail server stopped, the registration still behaves sanely, the failure is visible in the logs, and nothing is left half-broken.
Level 3If you get thereOnly once 1 and 2 work
  1. The eleventh send to one address in 24 hours returns 429 / 4002.
  2. Mail sent through a real external provider to a real inbox.
  3. A formatted HTML email rather than plain text.

08Submitting it

  • Branch feature/registration-otp on your fork, PR opened against your own main, reviewer added
  • PR description says what you finished and — honestly — what you didn't
  • README explains how to run it from a clean clone, including every environment variable
  • Nothing secret committed, no IDE folders
  • Small commits with messages that say what changed and why
  • It compiles and starts

Then you get a code review — a conversation, not a score. Expect it to cover whether it runs on a clean machine, why the pending registration lives where it does, whether the envelope is built in one place, how mail and Redis are wired and what happens when they're down, and the code itself.

Bring the parts you're unsure about rather than hiding them. There's no mark to protect, so the conversation is the entire point — and "I couldn't work out how to do X" is a perfectly good thing to say in it.

09Your five days

Day 1Read this. Run the scaffold. Connect PostgreSQL, write your first migration, get one entity saving and loading.
Day 2Envelope and central error handling first — everything returns through it. Then the pending registration and POST /registrations, with validation and password hashing.
Day 3Email. Get a real code into the inbox. Start early — this is the day that surprises people.
Day 4Verify, account creation, transaction boundary. Move codes into Redis with a TTL and add attempt limits.
Day 5Resend rules, edge cases, README, and open the PR with time to spare.

When you're stuck

  • Ninety minutes on the same error is enough — ask. Struggling is where the learning is; losing a day silently isn't.
  • A good question has four parts: what you expected, what happened, the actual error, and two things you already tried.
  • Read the stack trace to the bottom. The useful line is usually after Caused by.
  • Search the concept, not your error message.
  • Use AI to understand things, not to produce them. If you can't explain your own repository in the review, the week gave you nothing.
